## 발견 사항
### 1. Demo: JPA로 읽은 공연 시각이 +9시간 (수정함, #46)
- **증상:** JVM 시간대가 KST인 PC에서 DB에는 UTC `09:00`이 저장돼 있는데, `/concerts` API는 `18:00Z`를 돌려줬습니다. BTS 공연 동기화에도 같은 값이 전달됐습니다.
- **영향 범위:** JdbcTemplate 경로(예매·이벤트·metadata의 `performanceStartsAt`)는 정상이었고, JPA 엔티티(`Concert`)만 영향을 받았습니다.
- **원인:** `hibernate.jdbc.time_zone=UTC` 상태에서 Hibernate가 `LocalDateTime`을 `Timestamp`로 바꾸며 JVM 시간대가 끼어들었습니다.
- **수정:** `hibernate.type.java_time_use_direct_jdbc=true` (8b28313). 수정 후 공연 시나리오 5개가 모두 통과했습니다.

### 2. BTS: 빈 DB에서 `schema.sql` 적용 실패 → ticket-fds-admin#46
- **증상:** `booking_history`·`user_card`는 `utf8mb4_unicode_ci`로 고정돼 있고, `user_account`는 MySQL 8 기본값(`utf8mb4_0900_ai_ci`)을 따릅니다. 그래서 FK를 만들 수 없습니다(ERROR 3780).
- **테스트 우회:** e2e 환경은 서버 기본 collation을 `utf8mb4_unicode_ci`로 맞춰서 진행했습니다.

### 3. BTS: JVM 시간대와 `serverTimezone`이 다르면 시각이 밀려 저장 → ticket-fds-admin#47
- **증상:** KST JVM에 `serverTimezone=UTC`로 실행하자 `behavior_event.occurred_at`이 −9시간으로 저장됐습니다.
- **테스트 설정:** README 기본값(`serverTimezone=Asia/Seoul`)에서는 정상이라 e2e는 이 값을 씁니다.
- **운영 위험:** 운영 JVM이 UTC라면 반대로 +9시간이 됩니다.
